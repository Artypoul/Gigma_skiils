# Стандарт DDD-архитектуры API

**По умолчанию — ревью и проектирование, а не правка.** Код, миграции и контракты не меняются, пока владелец явно не переведёт задачу из ревью в реализацию.

Нормативный текст — `references/standard.md`. Путь указывает **внутрь папки самого скила**, где лежит этот `SKILL.md`, а не внутрь рабочего проекта. Версию и дату проверки бери из шапки того файла: здесь они намеренно не продублированы.

## Сначала режим, потом чтение

Стандарт задаёт разный объём работы для разных задач, поэтому читать его целиком нужно не всегда:

| Режим | Читать разделы | Объём процесса |
|---|---|---|
| Локальная правка внутри уже описанного сценария | 2.1, 3 и 9 плюс те из разделов 4–8, что покрывают затронутое место | Gate 0 и Gate 5 в границах сценария |
| Ревью существующего API | весь документ: разделы 4–8 и есть предмет проверки, без них ревью пропустит retry-политику, изоляцию tenant'ов, сетевые вызовы в транзакции и контракт идемпотентности | все gates в режиме «восстановить и сверить» |
| Новый сервис или изменение контракта, инварианта, прав, денег, лимитов, схемы данных | весь документ | Gate 0–5 и полный набор артефактов |

Сокращение объёма объявляется строкой «gates сокращены: причина, затронутый scope». Молчаливое сокращение — нарушение стандарта.

## Жёсткое ядро

Действует в любом режиме, до и без чтения стандарта:

1. Статус `confirmed` даёт только доказательство из источника истины: проходящий тест на нарушающем кейсе, фактически сгенерированный OpenAPI, запрос к целевой схеме или данным. Тест засчитывается, лишь когда идёт против той же реализации и той же СУБД, что и целевая среда: прогон на моках, на другой СУБД или с иной конфигурацией даёт максимум `probable`. Миграция в репозитории доказывает намерение, а не развёрнутое состояние. Правдоподобное рассуждение, `HTTP 200` и «команда выполнена» доказательствами не являются.
2. Недоступную проверку оставляй `unverified` и возвращай явным списком «что проверить вручную» — умолчание читается как «проверено всё».
3. `production_ready` объявляет человек-владелец; миграции ревьюит человек.
4. Конфликт стандарта с ADR, политикой проекта или прямым указанием — фиксируй обе версии, риск и владельца решения, не выбирай молча.
5. Версии стека бери из lockfile и runtime проекта, а не из памяти модели.

Остальные правила живут в стандарте и здесь не дублируются.

## Отчёт

По структуре раздела 3 стандарта, объём — по выбранному режиму. Вердикт, блокеры и рекомендацию формулируй так, чтобы владелец продукта понял их без чтения кода: незнакомый термин поясняй одной строкой при первом употреблении. Технические подробности — в приложенный register, а не в вердикт.

## Смежные скилы, если установлены

- `project-context-bootstrap` и `read-code-first` (плагин `development-workflow`) — правила репозитория, git-контекст и живой код до выводов; дисциплина источников и недоверенного материала — `research-with-evidence` оттуда же, этот стандарт её не заменяет.
- `provisioning-flows` (плагин `codex-toolkit`) — создание и синхронизация внешних сущностей. В части неизвестного исхода вызова и реконсиляции он строже раздела 7 стандарта, поэтому при проектировании внешних вызовов берётся вместе с ним.
- `frontend-plan` (плагин `frontend-workflow`) — когда у той же задачи есть frontend-часть.
