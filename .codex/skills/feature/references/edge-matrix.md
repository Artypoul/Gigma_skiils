# Edge-matrix — злой самопроход перед первым push

Цель: внешний ревьюер (monster/Codex/Claude) находит в первом раунде не больше 1–2 замечаний. Всё, что ловится этим списком, чинится ДО первого push.

## Как применять

- **В плане (Шаг 1):** по каждому применимому пункту — строка в плане; неприменимые пункты помечай явно: «не применимо, потому что …».
- **Перед первым push (Шаг 4):** пройди список по актуальному diff в режиме «злого ревьюера». Задача — не «убедиться, что работает», а «сломать».
- **В self-review:** каждый пункт — либо ✅ с анкором (имя теста/файла), либо «не применимо, потому что …». Голое «всё хорошо» не считается.

## Данные и API (backend)

1. **Data loss** — может ли update случайно стереть старые данные?
2. **Partial payload** — что будет, если придёт только одно поле из формы?
3. **null vs omitted** — различаются ли «поле не пришло» и «поле пришло null»? Для PUT явно выбери: full-replace или patch-like (для форм профиля безопаснее patch-like: не пришло → не трогаем, null → осознанная очистка).
4. **Middleware** — какие висят на route group / global и могут изменить request до валидации? (route-level `withoutMiddleware` не отменяет global.)
5. **Special values** — 0, false, "", null, [], {} в payload проверены? Falsy-фильтр их не теряет?
6. **Multi-tenant** — нет доступа к чужому project_id / counterparty_id / application_id? Есть тест на изоляцию?
7. **Authorization** — 401 (нет входа) / 403 (нет прав) / 422 (бизнес-отказ) разделены и протестированы?
8. **Race / транзакции** — lock на нужной строке; внешние вызовы после commit; при неизвестном исходе операции нет слепого повтора; идемпотентность создающих операций.
9. **Обратная совместимость** — старый фронт / legacy endpoints / старые проекты не ломаются; миграции аддитивные (nullable, без drop/rename).
10. **Тест на потерю данных** — есть тест именно на тот сценарий, где данные могут потеряться или исказиться.

## Контракт с внешним API («контракт с натуры»)

11. **Настоящий ответ получен и сохранён**: curl к реальному серверу, тест бэкенда или код донора; ответ лежит в тестах как образец (фикстура). Писать разбор формата «по памяти» запрещено.
12. **Красный тест до фикса**: тест сначала доказывает дефект на старом коде, потом код чинится.
13. **Неизвестный статус/поле** — поведение fail-closed и видимое пользователю («статус уточняется»), а не тихое «данных нет».
14. **Сбой источника** (404 / 5xx / таймаут / рассинхрон каталога) — отдельная ветка с честной ошибкой, не маскируется под пустой результат.

## Frontend

15. **Что уже есть** — routes / components / API-клиент проверены, дубликаты не плодятся, существующий визуальный паттерн переиспользован.
16. **Состояния экрана** — loading / empty (`exists: false` — не ошибка!) / error / 401 / 403 / 422, каждое по-своему.
17. **Два пользователя** — новый без данных и старый с заполненными данными: оба сценария проходят.
18. **Payload safety** — undefined → поле не трогаем; null → осознанная очистка; 0 / false / "" — валидные значения, не теряются.
19. **Desktop и mobile** — оба экрана обновлены и показывают одно и то же состояние.
20. **Ссылки и redirect** — только http(s); внешние значения не попадают в `javascript:` / `data:`.

## Финальный вопрос

«Если ревьюер заставит это исправить — исправь до push».

## Ревью-в-правило

Если внешний ревьюер всё же нашёл класс ошибки, который мог быть пойман этим списком, — после починки добавь сюда одну строку тем же PR. Каждый класс ошибки внешнее ревью должно находить максимум один раз.
